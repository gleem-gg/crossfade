# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

Crossfade is a dual-mix virtual audio mixer for Linux (GTK4/libadwaita + PipeWire) and Windows (GTK4/libadwaita + WASAPI + its own virtual audio driver in `driver/`), written in Rust. Every input channel has two independent faders: a Monitor Mix (what the user hears) and a Stream Mix (exposed as a virtual microphone "Crossfade Stream Mix" for OBS/Discord). An optional third mix (off by default, toggled via the "Enable VOD Mix" menu item / `vod_mix_enabled` in the config) adds a VOD Mix per channel, exposed as a second virtual microphone "Crossfade VOD Mix" for a DMCA-safe recording track.

## Commands

```sh
make            # cargo build --release
make run        # cargo run (debug)
make check      # cargo clippy -- -D warnings  +  desktop-file-validate
make install    # installs binary/desktop file/icon to ~/.local (PREFIX=… to override)
```

The only tests are a couple of pure-logic unit tests in `src/config.rs` (`cargo test`, covering config migration and the app-rule matcher); `make check` (clippy with warnings denied) is the gate. Runtime needs PipeWire with `pipewire-pulse`; build needs `gtk4-devel libadwaita-devel pulseaudio-libs-devel alsa-lib-devel` (Fedora names).

Windows: build with the gvsbuild GTK4 bundle (`PKG_CONFIG_PATH=C:\gtk\lib\pkgconfig`, `C:\gtk\bin` on `PATH`, `LIB` including `C:\gtk\lib`), then `cargo build` / `cargo clippy -- -D warnings`. The kernel driver and its setup tool build with `driver\build.ps1` (VS 2022 Build Tools + WDK); see `driver/README.md` for test-signing and install. `CROSSFADE_ALLOW_NO_DRIVER=1` runs the app without the driver (monitor mix only). `packaging\windows\build-installer.ps1` builds everything and the Inno Setup installer (`crossfade.iss`): it stages the exe with its GTK DLL closure (via `dumpbin`), the app-local VC++ runtime, `gdbus.exe`, the SVG pixbuf loader, schemas and icon themes in a relocatable `bin/lib/share` layout. `build.rs` embeds `packaging/windows/gleem-crossfade.ico` (regenerate with `make-icon.ps1`) and version info into the exe. `gleem-crossfade --quit` asks a running instance to quit cleanly (the installer and uninstaller use it).

Diagnostic flags on the built binary (`--list-*` are Linux-only): `gleem-crossfade --list-lv2`, `gleem-crossfade --list-vst`, and `--hidden` (autostart mode: window starts hidden).

## Architecture

Single-threaded: everything — PulseAudio client API, child-process I/O, UI — runs on the GTK main loop (`libpulse-glib-binding` mainloop adapter). The only worker threads are transient startup warm-up scans (LV2 catalog via `lv2::warm`, VST cache); everything else is async via glib timeouts/idles and PulseAudio operation callbacks. Never call `lv2::catalog()` on a path that runs while the UI should stay responsive unless the warm-up has landed (`lv2::scan_pending()` / `lv2::when_ready`).

### Platforms

Shared code is platform-neutral; backends are picked with `cfg(target_os)` behind identical APIs: `audio::AudioManager` (`audio/pulse.rs` = `PulseManager` on Linux, `audio/wasapi/` = `WasapiManager` on Windows), `midi::MidiManager` (`midi/alsa_seq.rs` / `midi/winmm.rs`), `platform::{autostart_enabled, set_autostart}`, and `ui::tray` (`tray.rs` SNI / `tray_win.rs` Shell_NotifyIcon). Linux-only: effects (`fx`, `lv2`, `ui/effects.rs`; the strip's FX button is hidden elsewhere) — `vst.rs` stays compiled because its types are part of the config format. `ui/dbus.rs` compiles everywhere but only registers when the GApplication has a D-Bus connection. When adding an `AudioManager` method the UI calls, implement it in both backends.

### Modules

- `src/audio/pulse.rs` — `PulseManager`, the Linux routing core. Talks to PipeWire via the PulseAudio API. Creates one null-sink bus per mix (`Crossfade_Monitor`, `Crossfade_Stream`, plus `Crossfade_Vod` when the VOD mix is enabled), routes each channel through one `module-loopback` per mix (per-channel/per-mix volume+mute are plain sink-input operations on those loopbacks), exposes the stream and VOD buses as capture devices via `module-remap-source`, and drives level meters with low-rate peek streams. `apply_vod_mix` reconciles the server against `vod_mix_enabled` at runtime — creating/tearing down the VOD bus, mic, meter, and per-channel sends without touching monitor/stream wiring. Emits `AudioEvent`s consumed by the UI. `reconcile_apps` classifies every foreign playback stream on each refresh: the first `App` channel whose rules match wins, otherwise the catch-all channel takes it — unless the stream already sits on a `Crossfade_*` sink, which means the user pointed it there deliberately. Self-healing: re-applies volumes and re-attaches streams (both the sink and the capture side) if the session manager moves them; channels whose capture device is absent are parked and wired when it appears; cleans up stale `Crossfade_*` modules from crashed sessions on startup. Capture-before-playback ordering: the monitor-out loopback is deferred at startup (and bounced when a parked capture device on the same card appears) until capture loopbacks run, because the Wave XLR's firmware delivers a silent mic if its playback stream opens first; an 8s safety timeout guarantees monitor audio regardless.
- `src/audio/wasapi/` — Windows backend. Unlike Linux, mixing happens in-process: `engine.rs` is a real-time thread (MMCSS "Pro Audio", 5 ms ticks clocked by QPC) that pulls each channel's input (WASAPI capture, or loopback of a render endpoint), mixes the three buses and delivers the monitor bus to a hardware output and the stream/VOD buses to the driver's virtual microphones (`driver.rs`: s32 frames via a private KS property). Hardware clocks are decoupled with elastic FIFOs that drop/repeat single frames based on the minimum fill (slack) over a window — WASAPI moves 10 ms bursts, so averaged fill levels are useless for drift control. Channels that provide a device are backed by one of the driver's 8 fixed "Crossfade Channel N" render endpoints (`ChannelConfig::device_slot`, persisted), recorded via loopback; App/catch-all channels pin matching processes to that endpoint through the undocumented per-app default-device policy (`policy.rs`, as EarTrumpet does), and every pin is cleared on quit. `mod.rs` (`WasapiManager`, main thread) polls engine events, endpoint changes and playback sessions at 30 Hz/1 Hz. Driver endpoints are recognized by the KS topology filter reference string they hang off (`CfTopo*`), never by name. Endpoint names: Windows calls speaker-type endpoints "Speakers" regardless of the driver's pin names, so the setup tool names them "Crossfade Channel N" and an admin-rights naming service (`driver/setup/service.cpp`, pipe protocol in `crossfade.h`) renames them after channels ("Crossfade: Game") on request from `namer.rs`; `sync_endpoint_names` only sends when Windows' names differ, so call it after any change to channel names, roles or slots. UI text must use `AudioManager::channel_device_label`, never a hard-coded "Crossfade: <name>". Mix gains use PulseAudio's cubic curve so faders feel the same on both platforms.
- `driver/` — the Windows virtual audio driver (C++, PortCls WaveRT, root-enumerated) and `crossfade-driver-setup.exe`. `driver/inc/crossfade.h` is the contract with `audio/wasapi/driver.rs`.
- `src/config.rs` — serde config, persisted at `~/.config/gleem-crossfade/config.json`. `Assignment` enum defines the four channel input kinds: `Source` (capture device), `App` (playback streams matched against a list of `application.name` rules — plain names or `*`/`?` globs via `app_matches` — and moved into a per-channel null sink), `CatchAll` (every playback stream no `App` channel claims; at most one channel, enforced in `load`), `Virtual` (channel is itself a selectable output device "Crossfade: <name>"). The last three all expose that device, so `provides_device()` — not a `Virtual` match — is what decides whether a channel needs a null sink. Legacy single-app configs (`"kind": "app", "name": "Spotify"`) deserialize into a one-element list.
- `src/fx.rs` — `FxManager`, per-channel effect chains as child processes (tied to app lifetime via `PR_SET_PDEATHSIG`). Two helper kinds per channel: an LV2 chain (`pipewire -c <generated conf>` hosting `module-filter-chain`; conf generated under `~/.config/gleem-crossfade/fx/`; live control changes via `pw-cli set-param`) and a VST rack (`data/vsthost.py` embedded via `include_str!`, driving Carla's engine library headlessly over a JSON-lines stdin/stdout pipe). The VST helper is a JACK client, invisible to the PulseAudio API, so it's wired with `pw-link` against a dedicated null sink's monitor. VST rack processes first, then the LV2 chain. Structural VST changes (add/remove/reorder/enable) respawn the helper; parameter changes stream live. A crashed helper falls back to the channel's direct wiring.
- `src/lv2.rs` — LV2 discovery through liblilv, dlopen'd at runtime (`libloading`) so lilv is optional: without it the plugin browser is unavailable but existing chains still work (PipeWire instantiates them itself). Only 1-in/1-out and 2-in/2-out plugins are listed.
- `src/midi/` — `MidiManager`. Windows (`winmm.rs`): every WinMM input/output opened (single-client devices), callbacks forwarded through a channel drained on the main loop, hotplug by polling the device list. Linux (`alsa_seq.rs`): a duplex ALSA sequencer client ("Crossfade") on the GTK main loop (the seq poll fd is watched via a GIOChannel FFI shim in `watch_fd` — glib 0.22 dropped the `unix_fd_add` bindings). Auto-connects every controller, handles hotplug via the System:Announce port, and sends note-ons back for LED feedback. Controllers are identified by client *name* (stable across replugs); if the sequencer can't be opened MIDI is simply absent (`available()`). Fails soft — no thread, no panic.
- `src/vst.rs` — VST2/VST3 discovery via `carla-discovery-native` (probes each binary in a throwaway process); results cached in `~/.cache/gleem-crossfade/vst-scan-v2.json` keyed by path + mtime.
- `src/ui/` — `window.rs` holds the `App` struct wiring everything together; `channel_strip.rs`, `input_picker.rs` (the strip's input selector: a popover combining the single-choice input kinds with a checklist of running apps and free-text glob patterns; rows are rebuilt from an idle callback so a row is never destroyed inside its own handler), `outputs.rs`, `sidebar.rs`, `effects.rs` (the effects dialog, including live sync with a VST plugin's native editor window via `DialogHooks`), `setup.rs` (audio setup assistant: checks default output/input and Wave XLR routing, one-click fixes; auto-shown on first run, later misconfigurations raise a toast), `wave_xlr.rs` (Wave XLR volume dialog; stored levels are enforced for the first ~15s after start/device appearance — a one-shot write loses races against WirePlumber's route restore and the firmware's own resets — then the physical controls are left alone), `midi.rs` (MIDI controllers dialog: devices, options, binding profiles), `dbus.rs` (session-bus control API `gg.gleem.Crossfade.Mixer1` at `/gg/gleem/Crossfade/Mixer`, exported on the GApplication connection), `tray.rs` (StatusNotifierItem + its `com.canonical.dbusmenu`, hand-served over GDBus on that same connection — GTK4 has no status icon and this avoids a second D-Bus stack plus a thread; shows and toggles the microphone channel's mute, presents the window, quits. Best-effort: with no `org.kde.StatusNotifierWatcher` on the bus nothing is registered, and the watcher is watched so a later-enabled AppIndicator extension still picks the item up). Shared CSS lives in `ui/mod.rs`.
- Remote control (MIDI + D-Bus) funnels through `ControlAction`/`perform` in `window.rs`, which drives the *widgets* (`set_value`/`set_active` without the guard) so the existing signal handlers do the config write, server apply, link-follow and debounced save — one code path with the GUI. MIDI dispatch (`handle_midi_event` area in `window.rs`) adds fader pickup and CC rising-edge logic on top; MIDI learn is armed via `App.midi_learn` (right-click on any fader/mute, or on a strip's color bar to bind a `ChannelColor` locator pad — lit via the shared RGB pad palette in `midi.rs`, inert on press). MIDI bindings live in `config.midi` keyed by controller name + CC/note, grouped into profiles with stable ids; `SelectProfile` pads are global. The debounced save in `schedule_save` doubles as the D-Bus `StateChanged` emitter.
- `build.rs` compiles `data/gleem-crossfade.gresource.xml` (bundled symbolic icons) into the binary.

### Conventions and gotchas

- The UI follows the [GNOME Human Interface Guidelines](https://developer.gnome.org/hig/) and is built with GTK4 + libadwaita: prefer adwaita widgets (`adw::` over raw `gtk::` where an equivalent exists), symbolic icons, and HIG-conformant spacing, capitalization (header capitalization for buttons/titles), and dialog patterns.
- Everything created on the audio server is prefixed `Crossfade_` (e.g. `Crossfade_Ch<id>`, `Crossfade_Ch<id>_FX`); startup cleanup and self-healing depend on this prefix.
- Every loopback/meter stream gets a unique, stable `media.name` and **opts out of session-manager volume/target restoring** (see `loopback_args` in `audio.rs`) — without this WirePlumber "restores" streams onto whatever a same-named stream used in an earlier session. Preserve these properties on any new stream/module.
- Module arguments are string-built; descriptions pass through `sanitize_desc` to avoid breaking PulseAudio quoting.
- Config saves are debounced through `schedule_save` (`ui/window.rs`), but quit and window-close save immediately — closing the window only hides it (virtual devices keep running in the background); `app.quit` saves, unloads everything from the audio server, then exits.
- Effect chain node labels use the effect's stable `id` (unique per channel) so reordering doesn't break the generated filter-chain graph.
